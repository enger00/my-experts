## 二、⛔ WebVPN 单账号 = 单会话（本工程的**主约束**）

**这条约束与机器数、浏览器实例数无关**：同一账号换台电脑登录，照样把先前那台踢下线。
所以「买台新机器就能并行」是错的思路。

推论：

1. 所有 `needs` 含 `webvpn` 的通道，**必须共用 Chrome(:9223) 并串行执行**。
2. **但串行 ≠ 全程占满** —— 见第四节的「时间片填谷」，这是最容易被浪费掉的产能。

## 三、双实例分工（唯一可行的真并行）

```
Chrome :9223  ── 登 WebVPN ──→  万方 / 知网 / yiigle / Springer / IEEE / SD   （VPN 轨，组内串行）
Edge   :9224  ── 不登 VPN  ──→  OA / PMC（公开资源，不需要机构权限）          （自由轨，可并行）
```

> ⭐ **端口是 `:9224`，不是 `:9222`**：`:9222` 是旧 `start_edge_debug.py` 的端口，
> **它的启动页就是 `wvpn.ncu.edu.cn/auth/login`** —— 一旦被拉起就会去登 WebVPN，从而踢掉 Chrome 的会话。
> ⚠ **VPN 只登在 Chrome 上，Edge 本不承载 VPN**；问题出在**那个脚本的启动页**，不在 Edge 本身。
> OA 专用实例（`tools/start_edge_oa.py`）用**独立端口 + 独立 profile `edge-profile-oa`**、
> 启动页 `about:blank`，**从设计上就不可能碰 wvpn**。

**编排器怎么自动分组**（不必靠人记）——`tools/flow_channels.py`：
```python
lane_of("oa")    # -> "free"   免 WebVPN ⇒ 可与 VPN 轨并行
lane_of("cnki")  # -> "vpn"    占单账号会话 ⇒ 必须串行
lanes()          # -> {"vpn": [wanfang, cnki, yiigle, sd, ieee, springer],
                 #     "free": [oa], "http": [...], "n/a": [cqvip, zhangqiao, webvpn_locked]}
```
判据从 `needs` 推导：含 `webvpn` ⇒ VPN 轨；只含 `cdp` ⇒ 自由轨。
新增通道时**只改登记表**，编排逻辑自动跟上。

⛔ **纪律（违反即互踢）**：自由轨实例（**:9224**）**绝不能访问 `wvpn.ncu.edu.cn`**。
一旦在那里登录，Chrome 的主会话立刻被踢，正在跑的分片会全线失败。

⛔ 两个实例**不得操作同一站点**（脚本会各自 `navigate` 自己的页面，互相打断）。

> 另有一批**纯 HTTP、不占浏览器也不占 VPN** 的通道，随时可与任何东西并行：
> PubMed E-utilities（1.5s 节流）、`link.cnki.net/doi/<DOI>` 解析、知网空间公开页
> `www.cnki.com.cn/Article/CJFDTotal-*.htm`、Crossref / OpenAlex / Unpaywall 元数据。
> ⚠ 其中打**知网域**的那两个，保守起见不要与知网下载同时跑。

## 四、⏱ 时间片填谷（回收闲置产能）

以下用**旧参数** `--shards 3 --per-shard 25 --gap 50 --cool 1800` 的**实测**时间轴为例
（该参数组合已因风控降级为 `--gap 75`，见第六节；旧数据仅用于估算窗口）：

| 时间段 | 占用 | 备注 |
|---|---|---|
| 0–27 min | 知网第 1 片 | 实测 25 条 / 27 分钟 |
| **27–57 min** | **冷却（CDP + WebVPN 全空闲）** | ← **填谷窗口** |
| 57–84 min | 知网第 2 片 | |
| **84–114 min** | **冷却** | ← **填谷窗口** |
| 114–141 min | 知网第 3 片 | |

**旧参数下闲置占比 42.5%。** 但 ⚠ **新默认 `--shards 2 --gap 75` 下窗口缩到一个 30 min 冷却窗**
（每片因 gap 拉长而变慢）⇒ **填谷收益下降，换来的是不撞风控，这笔交换是划算的**。

冷却只是让**知网侧**的请求密度降下来，并不要求整个 WebVPN 闲着 ⇒
该窗口应让给其他 webvpn 通道：

- ✅ 填**英文**侧：Springer / IEEE / SD（仍有真实缺口）
- ⛔ 别填**中文**侧：万方 / yiigle **已排干**（守护连续 EMPTY、`pdf_status` 0 态与 4 态均为 0），无活可填

⛔ 填谷四条纪律：
① 只在 `run_cnki_shards.sh` 处于 `sleep` 冷却时启动（严格互斥）；
② 同站点绝不并行；
③ 填谷任务也要有自己的节流与退出码判定；
④ ⭐ **知网片运行期间，自由轨也不与它并行**（09-21 新增护栏）——见下节。

## 五、并行的真实天花板

**不是会话数，而是风控阈值。**

- 知网：同一账号连续 20~30 篇即弹验证码 ⇒ **给它 10 个会话也不能提速**。
- SD：请求密度过密即限流（冷却 ≥半天、gap ≥25s）。
- ⇒ 并行只能「**跨站点**」，不能「**对同一站点**」。

### ⛔ 并行护栏（09-21 新增，成因待验证）

**已知代价（实测）**：知网第 2 片与 OA 并行时，成功率 **100% → 80%**、均耗时 **16.9s → 29.3s（+73%）**；
**随后**第 3 片第 1 条即弹拼图风控（当日累计放到第 46 条）。

⇒ 时间上吻合「**同一出口 IP 并发 ⇒ 知网风险分升高**」，但这**只是相关性、不是因果**，不许当结论引用。

**处置**：在 A/B 实测跑出数字之前，**知网片运行期间自由轨一律不与之并行**；
OA 挪到冷却窗口内或其后再跑。并行的默认适用范围从此收窄为：
**低价值通道 × 主通道明确闲置的窗口**。

**待做实验（团队 SOP 的 C 方案）**：对照＝知网独占 25 条；实验＝知网 + OA 并行 25 条；
同口径比成功率与均耗时。⛔ 会消耗主通道额度 ⇒ 只在知网恢复后做，且当日不再叠加其他知网任务。

## 七、想彻底解除单账号限制（须机构配合）

| 路径 | 说明 |
|---|---|
