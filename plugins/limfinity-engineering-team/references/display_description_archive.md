## en

Limfinity engineer: data sync (WPS / run_script), dashboard HTML rendering, Taro miniprogram with dual backend (Supabase + CloudBase, account/password auth), VM ops, and WeChat DevTools CLI automation (preview / upload / auto-screenshot), and N1 public tunnel (standalone frpc + Alibaba Cloud Caddy) to expose internal Limfinity /api over an ICP-filed domain, synced to CloudBase via the limfinityProxy cloud function. Plan C public read path uses a dedicated frp reverse-tunnel instance (the relay host dials out, .56 stays passive) instead of WireGuard. Never judge the tunnel by probing the frp remotePort externally: the security group blocks it, so it is always CLOSED even when healthy; verify end-to-end over HTTPS. See references/supabase_sync.md section 9. Custom-field sync: definitions live on SubjectType#properties (not DB columns) and values come from subject.get_value(name); when a Limfinity API is unknown, return introspection instead of guessing. Supabase upsert must use Prefer resolution=merge-duplicates. See section 10. Section 11 covers Supabase self-host ops (Envoy replaces Kong, docker compose service names only, Studio Basic Auth password change requires rebuilding api-gw, Chrome caches Basic Auth so verify in incognito). Plan C also registers the Node poller / frpc tunnel as a Windows service via nssm (auto-start, crash self-heal). PowerShell pitfall: nssm's 'Can't open service!' stderr, when suppressed with 2>$null, is still wrapped as a NativeCommandError that aborts the script; use 2>&1 | Out-Null with a $LASTEXITCODE check instead. '&' is the call operator, not a separator. See section 12. Plan C also stores Limfinity file attachments in Supabase Storage via a standalone upload worker (decoupled from the master sync to avoid >120s timeouts): FileProxy bytes are PUT to internal .56:8000 over the LAN, public URLs written back to master_data. Guard Encoding::CompatibilityError with safe_str+deep_scrub. See section 13. A Helper Script can serve BOTH a ScheduledScript (selected directly, no nginx 120s limit) and the run_script API (subject to that limit) from one single registration: never wrap a thin shell script that loops back through Net::HTTP to /api/run_script, because that re-enters the very nginx timeout you were trying to avoid. Parameterize timeouts/batch/total-time-budget via data[...] so the two entries get different limits without a code change. Because the API can only execute already-registered scripts (it cannot create or schedule them), every script edit needs a manual re-paste in the .46 admin, so scripts must be self-diagnosing: classify failures by root cause and record the returned value's class (not just a total count), so a single run reveals whether an error is retryable or structurally unfixable. To tell 'script not registered' from 'I called it wrong', run a known-registered script as a positive control. See references/run_script_push_sync.md section 8. IMPORTANT LIMIT to the dual-entry design: it only holds for lightweight scripts. A script that iterates over many Subject records (dozens or more) can ONLY run as an internal ScheduledScript - triggering it via /api/run_script always returns 504 regardless of parameters (verified with 137 records: even a minimal time_budget:5 still 504s). Root cause: the startup phase (loading Subject records through the Limfinity DSL/ORM) alone takes ~120s and hits nginx proxy_read_timeout, and an in-script time budget only bounds the business loop, not startup. Diagnostic: run once with minimal parameters; if it still 504s, parameter tuning is pointless and you must switch to internal execution. By contrast mini_sync_schema, which only iterates field definitions, returns success in seconds. Keep the cron interval larger than the worst-case single run (startup ~120s plus budget 240s), i.e. at least 10 minutes. Also: a stray lone CR inside an agent .md frontmatter description breaks YAML parsing (scanners treat CR as a line break); Python text mode hides it via universal newlines, so detect it in binary mode. Also: Taro build must rename dist (mv dist dist_prev) rather than rm -rf dist (safe-delete guard blocks bulk deletes). Limfinity script runtime model in references/limfinity_script_runtime.md; expert-pack maintenance rules in references/expert_maintenance.md.
